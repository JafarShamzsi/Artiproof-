# Alembic Migrations

SQLAlchemy is the source of truth for the schema. The Prisma schema in
`frontend/prisma/schema.prisma` is kept for historical reference only and is
no longer applied to the DB.

## Operating procedures

### Fresh database (no schema yet)

```bash
cd backend
alembic upgrade head
```

This runs `0001_baseline` (creates the original Prisma-equivalent schema)
followed by `0002_phase3_indexes_enums_constraints` (adds enums, indexes,
soft deletes, scoring transparency, etc.).

### Existing database (already has the Prisma-pushed schema)

```bash
cd backend
alembic stamp 0001_baseline   # mark baseline as applied without re-running DDL
alembic upgrade head          # applies 0002 onward
```

You only stamp once. After that, treat the DB as Alembic-managed and use
`alembic upgrade head` for every future migration.

### Generating a new migration

```bash
cd backend
alembic revision --autogenerate -m "short description"
# review the generated file in alembic/versions/, edit if needed, then:
alembic upgrade head
```

The autogenerated SQL is a starting point — review it before applying. In
particular, autogen does not always pick up enum value changes, server
default changes, or check constraints.

### Configuration

`alembic/env.py` reads `DATABASE_URL_SYNC` from `app.config.settings`. There
are no credentials in `alembic.ini`. To target a different DB:

```bash
DATABASE_URL_SYNC=postgresql://user:pass@host:5432/db alembic upgrade head
```

## Patterns for low-downtime migrations

Most production migrations should follow these rules. The Phase 3 migration
demonstrates each one.

### Adding a column

```python
op.add_column(
    "source_checks",
    sa.Column("new_col", sa.String(), server_default="default_value", nullable=True),
)
```

- Always nullable at first, even if you eventually want NOT NULL
- Use `server_default` so existing rows don't need a backfill migration
- If you need NOT NULL: add nullable, backfill, then `op.alter_column(... nullable=False)`
  in a *separate* migration so the backfill can run without holding a long lock.

### Adding an index on a large table

In a migration:

```python
op.create_index("ix_foo_bar", "foo", ["bar"])
```

This locks writes during the build. For large prod tables, run the
equivalent `CREATE INDEX CONCURRENTLY` out-of-band first, then create an
empty migration that records the change:

```sql
-- out-of-band (psql), no transaction:
CREATE INDEX CONCURRENTLY ix_foo_bar ON foo (bar);
```

```python
# inside the migration: no-op so dev/CI still creates the index
op.execute(
    "CREATE INDEX IF NOT EXISTS ix_foo_bar ON foo (bar)"
)
```

`CREATE INDEX CONCURRENTLY` cannot run inside an Alembic transaction, so
embed it via raw SQL with `op.get_context().autocommit_block()` if you need
it inline.

### Adding a CHECK constraint

```python
# Migration A — apply to new writes immediately, no scan, no long lock
op.execute("ALTER TABLE foo ADD CONSTRAINT ck_foo CHECK (x > 0) NOT VALID")
```

```python
# Migration B (separate file, deployed later) — validate existing rows
op.execute("ALTER TABLE foo VALIDATE CONSTRAINT ck_foo")
```

`NOT VALID` enforces the constraint on new writes without scanning the
existing table. `VALIDATE CONSTRAINT` reads the table without blocking
writers but still takes a SHARE UPDATE EXCLUSIVE lock — it must run in its
own transaction to be useful.

> **Note:** Alembic wraps each migration in a single transaction, so doing
> both steps inside one migration gives you no downtime benefit over a plain
> `ADD CONSTRAINT`. Phase 3 does both in one file because the tables are
> small and pre-launch. For production tables with significant rows, split
> the steps across two migrations as shown above.

### Renaming a column or table

Two-step deploys: add the new name, dual-write, deprecate the old. Single
ALTER is fine on small tables but locks the table on large ones.

### Changing a column type

Cast in place where compatible:

```python
op.execute(
    "ALTER TABLE foo ALTER COLUMN bar TYPE check_status USING bar::check_status"
)
```

For non-trivial conversions, add a new column, dual-write, then drop the
old one across two deploys.

## Naming conventions

`backend/app/models/base.py` sets a metadata naming convention so
autogenerated constraints and indexes follow a predictable pattern:

| Kind | Pattern |
|---|---|
| index | `ix_<table>_<col>` |
| unique | `uq_<table>_<col>` |
| check | `ck_<table>_<name>` |
| foreign key | `fk_<table>_<col>_<referred_table>` |
| primary key | `pk_<table>` |

When writing migrations by hand, use these names so future autogen diffs
stay clean.
